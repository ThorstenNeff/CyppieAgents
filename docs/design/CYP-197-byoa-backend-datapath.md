## 0. Der Datenpfad in einem Satz
Operator `POST /api/agents {remote:true}` → der Server **mintet ein per-Agent-Token** (einmalig-OOB in `CreatedAgent.token`), markiert den Agenten **no-spawn** (kein Prozess, kein Worktree, `worktreePath=null`) und gibt ihm einen **Spoke in der Hub-and-Spoke-ACL**. Der BYOA-Agent läuft in **Nutzer-Infra** (`:remote-runtime`-Bridge) und dialt `GET /ws/hub` mit dem Bearer → der Hub löst **`token→agentId` auth-first** auf (nie ein Frame-Feld), clampt die Capabilities **strukturell auf REMOTE**, und registriert eine `WireConnectorSession`. Ab da ist der Agent **ein normaler Spoke-Teilnehmer**: eingehende Hub-Nachrichten fließen durch den **connector-agnostischen `MessageDeliverer`** (→ `WireDeliver`), ausgehende durch den **einen `Hub.postAsAgent`-Chokepoint** (canWrite · server-gestempelte `from`/`projectId` · Mask · Size-Cap · Rate-Limit). **Identität ist immer das Token; die Wire liefert nie agentId/role/projectId.**

## 1. Erstellung + Token-Mint (BUILT)
- **Wire-Contract (`:core AgentMgmtModel.kt`):** `NewAgentSpec.remote: Boolean=false` — „nicht lokal gespawnt; der Server mintet ein per-Agent-Token, der Agent tritt über `/ws/hub` bei; Identität=`token→agentId`; **kein client-supplied agentId/role**." `CreatedAgent(agent, token: String?=null)` — `token` non-null **nur** beim Remote-Create (die **einzige** Offenlegung des geminteten Bearers; `GET /api/agents`/`AgentDetail` tragen nie ein Token). `AgentDetail.worktreePath: String?=null` für Remote (CYP-315).
- **`AgentManagement.add(spec)` (BootOrchestrator-verdrahtet):** `remote=true` ⇒ (a) NICHT in den CYP-256-Projekt-Agent-Store (Overlay-Pfad bleibt), (b) `token = remoteToken.issue(agent.id)` (`RemoteTokenIssuer`→`TokenRegistry.mint` 256-bit SecureRandom base64url + `RemoteTokenStore.put` 0600, nie geloggt), (c) `remoteAgents.add(id)`, (d) `CreatedAgent(agent, token)`. `detail(id)`: `id in remoteAgents ⇒ worktreePath=null`. CLAUDE.md-Endpunkte werfen `agent_not_local` (kein Worktree). Boot seedet `initialRemoteAgents = config.agents.filter{it.remote}`.

## 2. Identität / Auth-Pfad (BUILT — die Kern-Invariante)
- **Sole identity source:** `TokenRegistry.agentFor(token): String?` (`Auth.kt`). `/ws/hub` löst den Bearer **VOR jedem Frame** auf (auth-first); ein Operator-Token/unbekannt/absent → `close(VIOLATED_POLICY)`. **Kein Frame trägt Identität** — `WireHello` (keine trust/agentId/projectId), `WireSend` (kein `from`/`projectId`) — alles **server-gestempelt** in `Hub.postAsAgent`.
- **★ Symmetrie zur Aktivierungs-Wurzel:** dasselbe Prinzip wie der CYP-508/512-`ownerId`-nie-aus-Payload-Root — die **Identität kommt aus dem authentifizierten Credential, nie aus dem Client-Body**. Für BYOA ist das Credential das per-Agent-Token; `agentFor` ist der einzige Auflöser.
- **Rolle + Spoke:** der `role` kommt aus `NewAgentSpec.role` (operator-supplied beim Create, nie wire-self-asserted). `HubState.addAgent` gibt einem WORKER einen Spoke `po-<id>` (members `[po, id, operator?, +PL read-only]`, projectId-gestempelt) und rebuildet die `AclMatrix`. Ein Remote-Agent ist **nur ein weiteres Spoke-Mitglied** — kein Sonder-ACL-Pfad; `AclMatrix` (member AND flag, deny-wins) ist die eine Entscheidungsstelle für REST + Deliverer + Wire.

## 3. Connector-Naht + Mediation (BUILT, mit einer benannten Lücke)
- **Der lokale vs. der Remote-Connector:** `ConnectorRouter` (CYP-122) resolved beim **Spawn** `STREAM_JSON→ClaudeCodeConnector` / `MCP→McpConnector` — **hat KEINEN Remote-Zweig** (ein Remote-Agent wird nie gespawnt, also nie geroutet). Stattdessen ist der Remote-Connector die **`WireConnectorSession`** (CYP-141): ein `ConnectorSession` (`:connector-core`), der von der `/ws/hub`-Verbindung getragen wird — `sendTurn(turn)=WireDeliver(turn.text)` über die WS; `close()=closeWs()`.
- **Wie der Hub mediiert (der Kern der Frage):** der **`MessageDeliverer` (CYP-132) ist connector-AGNOSTISCH.** Die `WireConnectorSession` wird in `ConnectorSessions` **identisch** zu einer lokalen stdio-Session registriert → der Deliverer liefert an sie **gleich**:
  - **Inbound (hub→remote):** `Hub.postAsAgent` → `onPosted` → `drain(agentId)` reconciled sichtbare Kanäle via `AclMatrix.visibleMessages` (project-scope + canRead + CYP-93-Shares) gegen den `MessageStore`, dedupt via `DeliveryLog.isDelivered` (per `message.id`, R3), ruft `session.sendTurn(inboundTurn(m))` → für Remote ein `WireDeliver`-Frame → `log.markDelivered` (nach Erfolg ⇒ at-least-once). `EventProjector.commReceived` = metadata-only.
  - **Outbound (remote→hub):** `WireSend` → **derselbe `Hub.postAsAgent`-Chokepoint**, den auch die lokale Mediation nutzt (canWrite-403 uniform · `from`/`projectId` server-gestempelt · Mask · Size-Cap A5 · `WireRateLimiter` FIRST).
  - **Kein server-seitiger Prozess/Worktree/stdio:** Boot `if(agent.remote) lifecycle.register(id, STOPPED)` + Log „awaiting /ws/hub" (CYP-169).
- **BYOA-Seite (Nutzer-Infra):** `:remote-runtime` (`BridgeMain`/`WireLink`/`BridgeRelay`) dialt `/ws/hub` mit `HUB_TOKEN`, sendet `WireHello`+`WireSubscribe(spoke)`, mappt inbound `WireDeliver`→lokale `ClaudeCodeSession.sendTurn`, outbound Turn-Ergebnis→`MediationGate.classify`→`WireSend`. Reused `:connector-core`.

## 4. Capability-Trust (BUILT — der Trust-Boundary)
- **Strukturell REMOTE, nie frame-derived:** beim `WireHello` clampt der Hub `CapabilityCeiling.clamp(f.capabilities, ceilingFor(REMOTE))` — der **einzige** Caps-Ingress einer Wire-Agent. `REMOTE_CEILING`: `structuredUsage=UNAVAILABLE` (billing-kritisch, unverifizierbar), `toolGranularity/reliableResult/rateLimitSignal=LIMITED`, `coordination=AVAILABLE`. Clamp nimmt pro Dimension das Restriktivste ⇒ eine REMOTE-Lüge **degradiert, eskaliert nie**. (LOCAL-Ceiling=all-AVAILABLE ⇒ Identität.)
- **Der Trust-Boundary:** der BYOA-Agent läuft in **untrusted Nutzer-Infra**. Die drei Struktur-Garantien sind der Boundary: (1) Caps strukturell REMOTE-geclampt, (2) Identität server-gestempelt (token→agentId, nie Frame), (3) alle Writes durch den einen `postAsAgent`-Chokepoint (ACL + Mask + Size-Cap + Rate-Limit).

## 5. Was GEBAUT ist vs. STUBBED/DEFERRED
**GEBAUT + gemergt:** Wire-Contract (`remote`/`token`/`worktreePath=null`) · Token-Mint+Custody (`RemoteTokenIssuer`/`RemoteTokenStore` 0600) · `/ws/hub` auth-first + REMOTE-clamp + `WireRateLimiter` + Size-Cap + Slow-Loris-Reap · `WireConnectorSession` + connector-agnostische Mediation (Deliverer/DeliveryLog/at-least-once) · server-assigned Identität/Spoke/ACL · `:remote-runtime`-Bridge · durable `AgentEventStore` (WireEvent-Self-Report persistiert) · Live-e2e `RemoteBridgeSubprocessE2eTest` (CYP-199, RUN_CYP199-gated: realer /ws/hub + reale Bridge-Subprocess).

**STUBBED / DEFERRED (die ratifikations-relevanten Residuen):**
- **★ Observability-Lücke:** `WireConnectorSession.events = emptyFlow()` — der Server empfängt **NIE den rohen Prozess-Stream** eines Remote-Agenten (kein stream-json). Der Scanner/Warden-Beobachtungs-Kanal ist eine **benannte E2.6-Deferral**. Der `WireEvent`-Self-Report (Rate-Limit/Tool, LIMITED caps) ist der **Teil-Ersatz**, nicht volle Stream-Fidelity.
- **Structured-Usage aus:** REMOTE `structuredUsage=UNAVAILABLE` ⇒ **kein Token/Usage-Accounting** (unverifizierbar) ⇒ Remote-Agenten tragen **kein Billing** bei.
- **Kein Router-Zweig:** `ConnectorRouter` kennt Remote nicht (kein Spawn) — bewusst; der Wire-Pfad ist die „Connector-Impl" für Remote.

## 6. Offene Design-Fragen für den Auftraggeber (was zu ratifizieren ist)
Der Datenpfad steht; diese vier Punkte sind **Posture-Entscheidungen**, die der Auftraggeber ratifiziert (keine Blocker, aber sichtbar zu machen):

1. **Token-Lifecycle / Revocation.** Das per-Agent-Token wird **einmal** geminted (OOB) und ist **langlebig** (kein Ablauf). `TokenRegistry.revoke`+`RemoteTokenIssuer.revoke` existieren (drop token+store). **Zu ratifizieren:** (a) Braucht ein BYOA-Token **Rotation/Ablauf** (heute langlebig wie ein API-Key)? (b) Beim Revoke: wird eine **LIVE `/ws/hub`-Verbindung sofort gekillt** (heute: der nächste `agentFor` schlägt fehl, aber eine bestehende WS läuft bis zum nächsten Frame/Reconnect)? (c) Re-Issuance-Flow (neues Token → OOB → Bridge-Reconnect)? — **Empfehlung:** langlebig+revocable für MVP (wie ein Agent-API-Key), Live-Kill-on-Revoke als kleine Härtung, Rotation als Zukunft. Analog zur CYP-484-Op-Session-TTL-Diskussion.
2. **BYOA-Agent in der Hub-and-Spoke-ACL.** Ein Remote-Worker bekommt heute denselben Spoke `po-<id>` wie ein lokaler Worker. **Zu ratifizieren:** (a) Ist die **gleiche Topologie** richtig (BYOA=lokaler Worker in der ACL)? (b) Darf ein BYOA-Agent **PO** sein (Nabe), oder nur WORKER? (c) **Cross-Project** — kann ein mitgebrachter Agent mehreren Projekten beitreten, oder ist er projekt-gepinnt (heute: projectId-gestempelt, ein Spoke)? — **Empfehlung:** BYOA=WORKER-only, projekt-gepinnt für MVP (die ACL ist ohnehin flexibel; PO-Nabe für einen untrusted mitgebrachten Agenten ist eine bewusste Eskalation).
3. **Connector-Typ-Abgrenzung + Observability-Contract.** LOCAL (stdio, gespawnt, Worktree, all-caps, voller Stream für Scanner/Warden) vs REMOTE (wire, no-spawn, kein Worktree, REMOTE-clamped, **nur Self-Report**). **Zu ratifizieren:** ist der **`WireEvent`-Self-Report ausreichend** für die Mediator-Aufsicht (S11 Scanner/Warden) eines BYOA-Agenten, oder braucht BYOA einen **verpflichtenden Observability-Contract** (der Bridge muss z.B. Turn-Boundaries/Tool-Calls melden)? Heute ist die Aufsicht bei Remote **strukturell schwächer** (emptyFlow). — **Empfehlung:** Self-Report als MVP-Boden explizit ratifizieren + „fuller BYOA observability contract" als benanntes Zukunfts-Ticket (nicht MVP).
4. **Billing-Posture für Remote.** `structuredUsage=UNAVAILABLE` ⇒ Remote-Agenten sind **nicht abgerechnet**. **Zu ratifizieren:** ist das der gewollte MVP-Posture (BYOA=Nutzer-eigene Kosten, keine Server-Abrechnung), oder braucht BYOA einen **vertrauens-reduzierten Usage-Report**? — **Empfehlung:** BYOA=nicht-abgerechnet für MVP (der Nutzer bringt seinen eigenen Key/Compute); ein signierter Usage-Report ist Zukunft.

## 7. Scope / Ehrlichkeit
- **Design/Scoping only** — kein Bau ohne Auftraggeber-GO. Der Datenpfad ist **schon gebaut**; dieses Delta dokumentiert ihn ratifikations-reif + benennt die 4 Posture-Fragen + die 2 benannten Deferrals (Observability-Stream, Structured-Usage).
- **Abgrenzung zu Phase-2-Remote-Hub (CYP-427):** das ist ein **anderer** Strang — CYP-427 ist der Hub, der sich per Noise-Relay **outbound** an eine zentrale CP anbindet (Operator-Zugang über zentrale UI). CYP-197-BYOA ist der **mitgebrachte Agent**, der sich per `/ws/hub` an einen (lokalen ODER remote-erreichbaren) Hub anbindet. Beide teilen die Connector-Naht + `postAsAgent`-Chokepoint; die Trust-/Identity-Prinzipien sind symmetrisch (server-assigned, nie client-supplied).
