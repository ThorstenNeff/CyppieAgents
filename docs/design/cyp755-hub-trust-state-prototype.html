Hub-Trust-State — Design-Prototyp (5 Zustände)

CYP-755 · web-ts · gegen die PL-gefreezten Namen UNKNOWN / PENDING / TRUSTED / REJECTED / STALE

DESIGN-PROTOTYP — stub-parallel, NICHT merge-ready. Dies ist die Darstellungs-Referenz (Design-Deliverable), kein verdrahtetes Produktions-Bauteil. Die Produktions-Komponente in web-ts + die echten Signal-Teeth (F2: „kommt der State aus echtem Wire") sind Dev5 / CYP-798-gated. Gebaut gegen ein client-lokales Stub-Modell der gefreezten Namen; die :core-Enum-Verdrahtung landet mit CYP-798.

§1 Die fünf Zustände — Darstellung, Ton, a11y

Jeder Zustand trägt eine distinkte Glyph-Form + ein distinktes Wort → colour-never-sole (WCAG 1.4.1): in Monochrom unterscheidbar. Farbe = nur Verstärkung.

ZustandBadge (Glyph+Wort)TonRegeltestid
UNKNOWN ◯ Vertrauen nicht geprüft neutral fail-closed Default aus Abwesenheit (F4) — sichtbar, nie Stille, nie grün hub.trust.{id}.unknown
PENDING ◔ wird geprüft… neutral distinkt von UNKNOWN — nur bei echt laufender Verifikation hub.trust.{id}.pending
TRUSTED ● vertraut positiv (einziger) nur hub-ausgestellt; abgeleitet/widerrufbar, nie natives Identsein hub.trust.{id}.trusted
REJECTED ⊘ abgelehnt warnend nur echter Trust-Eval-Reject (+ TrustRejectReason) — nie aus malformed/Netz hub.trust.{id}.rejected
STALE ◑ abgelaufen — erneut bestätigen handlungs-neutral war trusted, widerrufen/abgelaufen → Surfaces nicht mehr live hub.trust.{id}.stale

a11y je Zustand: Container role="status", aria-live="polite"; aria-label = das Wort (nie nur Glyph/Farbe). Assertive-Ausnahme: ein Wechsel des aktiven Hubs in REJECTED/STALE (handlungsrelevant) → aria-live="assertive" / role="alert". Nur dieser aktive-Hub-Wechsel ist assertiv — die stille Switcher-Liste nicht (kein Ansage-Sturm).

§2 Kontext A — aktiver-Hub-Indikator (always-visible Chrome-Strip)

Zeigt den echten Zustand des aktiven Hubs — ein toter/abgelehnter Hub rendert REJECTED/STALE/UNKNOWN, nie optimistisch „wird geprüft".

◯ Vertrauen nicht geprüftaktiver Hub · UNKNOWN (aria-live polite)
◔ wird geprüft…aktiver Hub · PENDING (polite)
● vertrautaktiver Hub · TRUSTED (polite)
⊘ abgelehntaktiver Hub · REJECTED → assertive
◑ abgelaufen — erneut bestätigenaktiver Hub · STALE → assertive

§3 Kontext B — Hub-Switcher (Liste + aktiver-Pointer, Q4 one-active)

Jeder Eintrag trägt sein eigenes Glyph; nicht-frische inaktive Hubs rendern UNKNOWN, nicht das letzte gecachte trusted.

  • ▸● vertraut hub-alpha (aktiv)
  • ◯ nicht geprüft hub-beta
  • ◑ abgelaufen hub-gamma
  • ⊘ abgelehnt hub-delta

§4 PL-Freeze-Regeln — im Prototyp encodiert

  • malformed = Upstream-Error, NICHT Reject: ein uninterpretierbarer/malformed Wire-Wert rendert als ◯ Vertrauen nicht geprüft (fail-closed) mit optionaler Upstream-Fehler-Affordanz — nie als REJECTED (das wäre ein erfundenes Trust-Verdikt).
    ⚠ Upstream-Fehler — Status nicht lesbar (→ Zustand bleibt UNKNOWN; distinkt vom Trust-Reject)
  • PENDING distinkt von UNKNOWN: „wird geprüft" ist nie das Sammel-Label für nicht-verbunden/unbekannt.
  • TrustRejectReason nur für Trust-Eval-Rejects: der Reason-Code erscheint ausschließlich, wenn der Hub Trust wirklich evaluiert + abgelehnt hat — nicht bei malformed/Netz/Upstream.
  • UNKNOWN = fail-closed-Default aus Abwesenheit (F4): Abwesenheit einer Bestimmung → UNKNOWN, nie collapse-to-green; UNKNOWN ist sichtbar (nicht Stille).
  • Netzfehler ≠ Reject: transienter Netzfehler → Zustand UNKNOWN + „erneut versuchen", kein Trust-Verdikt.
